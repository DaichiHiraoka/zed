# Rendered Markdown Editor Spec

This document defines the behavior and implementation scope for a rendered
Markdown editor in Zed. The target experience is similar to VS Code extensions
such as Office Viewer: opening a Markdown file can show the converted document
inside the same editor tab, while edits made through the rendered document are
written back to the Markdown source file.

The feature is intentionally not described as "a better preview". It is a new
editing surface for Markdown buffers. Zed's existing Markdown preview must keep
working as a separate item.

## Product Goal

When a user opens `README.md`, they can choose a rendered editing mode in the
same tab. In that mode, the tab still represents the `README.md` file. The user
does not have to look at a second preview tab or split. The rendered document is
the primary surface, and direct edits on headings, paragraphs, lists, links,
checkboxes, images, and tables modify the underlying Markdown buffer.

The user must be able to switch between source mode and rendered mode without
losing selection, scroll position, unsaved changes, diagnostics, undo history,
or file identity.

## Non-Goals

- Do not remove or change the current `markdown::OpenPreview`,
  `markdown::OpenPreviewToTheSide`, or `markdown::OpenFollowingPreview`
  behavior.
- Do not implement this as a Zed extension. The current extension model is not a
  custom-editor or WebView API, so this feature belongs in the Zed application
  code.
- Do not make rendered mode a lossy rich-text format. The persisted file remains
  Markdown text.
- Do not invent a document model that permanently replaces the source buffer.
  The source buffer remains authoritative.
- Do not require an external browser engine.

## Existing Behavior Baseline

The existing Markdown preview lives in `crates/markdown_preview` and is an
independent workspace item:

- `MarkdownPreviewView::register` registers the three current preview actions.
  `OpenPreview` adds a preview item in the active pane, `OpenPreviewToTheSide`
  creates or uses a right split, and `OpenFollowingPreview` creates a preview
  item that follows the active Markdown editor.
- `MarkdownPreviewView` stores an `active_editor`, subscribes to editor events,
  debounces source changes, reparses the buffer into a `markdown::Markdown`
  entity, and renders a `MarkdownElement`.
- The preview already maps rendered positions back to source positions. A
  double-click in the preview can move the source editor cursor, and checkbox
  toggles already edit the source buffer.

That baseline is useful implementation material, but it does not satisfy this
feature because it opens a separate item and the rendered surface is mostly
read-only.

## Required User-Facing Modes

### Source Mode

Source mode is the normal Zed text editor for the Markdown file. It keeps all
current Zed behavior:

- raw Markdown text is visible
- syntax highlighting works
- selections, multiple cursors, find, replace, diagnostics, formatting, and
  Git diff markers behave as they do today
- existing Markdown preview actions still work

### Rendered Edit Mode

Rendered edit mode is a same-tab item state for the same Markdown buffer.

Required behavior:

- The tab title, dirty indicator, file icon, file path, close behavior, save
  behavior, and tab identity remain those of the Markdown file.
- The active item must still expose the underlying buffer as the item buffer so
  save, close, dirty checks, history, restore, and collaboration machinery see
  the real Markdown file.
- The rendered document becomes the primary visual surface.
- Clicking text places a caret in the rendered text.
- Typing edits the corresponding source Markdown range.
- Common rich editing commands convert to Markdown syntax.
- Undo and redo operate on the source buffer history, not on a separate rendered
  history.
- Switching back to source mode shows the exact Markdown source generated by the
  rendered edits.

### Split Source/Rendered Mode

This mode is optional for the first milestone but must be accounted for in the
architecture. It shows the source editor and rendered editor for the same
buffer inside one tab content area, not as two workspace tabs. It is useful for
debugging mapping issues.

Required later behavior:

- source and rendered panes share one buffer
- cursor and scroll synchronization can be enabled or disabled
- closing the tab closes both panes because there is still one file item

## Commands and Defaults

Add these actions under the `markdown` namespace:

- `markdown::ToggleRenderedEditor`
- `markdown::OpenRenderedEditor`
- `markdown::OpenSourceEditor`
- `markdown::ToggleSourceRenderedSplit`

Default keybindings should not replace existing preview keybindings. Suggested
bindings:

- `ctrl-shift-m`: toggle rendered edit mode
- `ctrl-k m`: open source/rendered split

Settings:

```json
{
  "markdown": {
    "default_open_mode": "source",
    "rendered_editor": {
      "enabled": true,
      "live_source_sync": true,
      "single_click_edits_text": true,
      "show_markdown_controls_on_selection": true,
      "table_editing": "structured",
      "unsupported_blocks": "source_fallback"
    }
  }
}
```

`default_open_mode` values:

- `source`: current behavior
- `rendered`: Markdown files open directly in rendered edit mode
- `last_used`: restore the last mode used for the same file or workspace

## Required Editing Behavior

### Selection and Caret

- Single click places the caret at the nearest editable rendered text position.
- Drag selects rendered text and maps it to one or more Markdown source ranges.
- Double click selects the rendered word.
- Triple click selects the rendered block: paragraph, heading, list item, table
  cell, or code block line depending on click location.
- `shift` + click extends the rendered selection.
- `ctrl+a` selects the rendered document and maps to the full source buffer.
- Copy copies rendered plain text by default.
- Copy with source modifier, if implemented, copies the underlying Markdown.
- Cut deletes the mapped Markdown range and writes rendered plain text to the
  clipboard.
- Paste plain text inserts plain text escaped as needed for the current Markdown
  context.
- Paste HTML converts to Markdown where possible.
- Paste Markdown inserts Markdown directly when the clipboard clearly contains
  Markdown.

### Typing

Typing in paragraph or heading text replaces the rendered selection or inserts
at the caret. The implementation must preserve surrounding Markdown delimiters
unless the user's edit explicitly removes the formatted region.

Examples:

- In rendered text `hello` from source `**hello**`, inserting `!` after `hello`
  produces `**hello!**`.
- Selecting rendered `hello` from `**hello**` and typing `world` produces
  `**world**`.
- Selecting the entire bold span and pressing Backspace removes the whole
  source span.
- Typing at the end of a heading source `## Title` produces `## TitleX`, not a
  new paragraph.

### Paragraphs

- `Enter` inside a paragraph splits the paragraph at the caret.
- `Shift+Enter` inserts a hard line break using Markdown syntax that preserves
  rendering.
- `Backspace` at the start of a paragraph joins with the previous block.
- `Delete` at the end of a paragraph joins with the next block.
- Empty paragraph handling must avoid generating unstable blank-line churn.

### Headings

Rendered headings are editable text blocks.

Required commands:

- set heading level 1 through 6
- convert heading to paragraph
- increase or decrease heading level

Behavior:

- Setting a paragraph to level 2 prepends `## `.
- Changing `## Title` to level 3 produces `### Title`.
- Converting `### Title` to paragraph produces `Title`.
- Pressing Enter at the end of a heading creates a paragraph below it.
- Pressing Enter in the middle of a heading splits the heading text and creates
  a paragraph below unless a later design explicitly supports split headings.

### Emphasis, Strong, Strikethrough, Inline Code

The editor must support direct formatting commands over rendered selections:

- bold
- italic
- strikethrough if supported by the parser/rendering path
- inline code

Behavior:

- Applying bold to plain selected text wraps it in `**`.
- Applying bold to an already bold selection unwraps the strongest matching
  delimiter.
- Applying italic inside bold creates nested Markdown without corrupting the
  outer delimiter.
- Applying inline code escapes backticks when needed.
- If a selection crosses incompatible block boundaries, the command applies to
  each block-local selection range or reports a non-destructive no-op.

### Links

Rendered links must be editable without immediately navigating away.

Behavior:

- Single click places the caret in the link text when rendered edit mode is
  focused.
- `ctrl` + click or command palette action opens the link destination.
- A link popover allows editing link text and URL.
- Changing only visible link text preserves the URL.
- Changing only URL preserves visible link text.
- Pasting a URL over selected text creates `[selected text](url)` when the
  selected text is not already a link.
- Pasting text over link text changes only the link label.

### Images

Images remain rendered as images but expose structured edit controls.

Behavior:

- Clicking an image selects the image node.
- The selection popover exposes alt text and destination.
- Typing while an image node is selected replaces the entire image syntax with
  text.
- Delete removes the image Markdown syntax.
- Drag-resize is not required for the first milestone because Markdown has no
  standard image sizing syntax.
- Local image resolution must reuse the current preview image resolver so
  relative paths resolve against the Markdown file first and workspace root
  second.

### Lists

Bulleted and ordered lists must be editable as structured list items.

Behavior:

- Enter at the end of a list item creates a sibling item with the same marker
  style.
- Enter on an empty list item exits the list.
- Tab indents the current list item.
- Shift+Tab outdents the current list item.
- Backspace at the start of a list item outdents first; if already top-level,
  converts to paragraph or joins with the previous block according to standard
  editor behavior.
- Ordered list numbering is normalized in the affected contiguous list region.
- Mixed ordered and unordered nested lists preserve marker type per level.
- Task list items are list items with a checkbox control.

### Task Checkboxes

The existing preview already supports checkbox toggles that write to source.
Rendered edit mode must keep and expand that behavior:

- Clicking the checkbox toggles `[ ]` and `[x]` without moving focus away from
  rendered edit mode.
- Toggling is a normal undoable source edit.
- The caret remains in the same list item when possible.
- Disabled or malformed checkbox syntax is rendered as normal text or falls back
  to source editing for that block.

### Code Blocks

Code blocks are editable, but the first milestone can use source fallback for
the code block body.

Required first milestone:

- rendered fenced code blocks show syntax highlighted code
- clicking a code block activates a source fallback editor for that block
- edits in the fallback editor update only the fenced block body
- changing the fence language is possible through a small control or source
  fallback line

Required later milestone:

- direct rendered code editing with caret, selection, indentation, and language
  syntax behavior inside the code block

### Tables

Tables are a major Office Viewer expectation and must be specified explicitly.

First milestone behavior:

- GFM-style pipe tables render as editable tables.
- Clicking a cell places a caret inside that cell.
- Typing edits that cell's source content.
- Tab moves to the next cell.
- Shift+Tab moves to the previous cell.
- Enter commits the cell edit and moves to the next row or inserts a line break
  only if multiline table cell support is later added.
- Context menu supports insert row above, insert row below, delete row, insert
  column left, insert column right, delete column.
- Alignment markers in the delimiter row are preserved.
- After structural edits, the table source is normalized to a readable pipe
  table.

Fallback behavior:

- If a table is malformed or cannot be mapped safely, clicking it opens a
  source fallback editor for the whole table block.
- The user must never silently lose table text or alignment markers.

### Frontmatter and Metadata Blocks

Frontmatter can render in the existing preview when metadata block rendering is
enabled. Rendered edit mode must avoid accidental destructive edits:

- YAML/TOML/JSON frontmatter is collapsed by default.
- Clicking the frontmatter area opens source fallback for that block.
- Metadata edits must preserve delimiters.
- If a file contains unsupported metadata syntax, it stays in source fallback.

### HTML Blocks

Markdown files often contain raw HTML. First milestone behavior:

- Safe inline HTML that already renders in preview can be displayed.
- Raw HTML blocks are source fallback blocks.
- Editing rendered HTML as rich text is not required.
- The source fallback must preserve the exact HTML unless the user edits it.

### Mermaid and Other Generated Blocks

Generated renderings are not rich-editable in the first milestone.

Behavior:

- Mermaid diagrams render like the current preview.
- Clicking the rendered diagram selects the block.
- Double-clicking opens source fallback for the Mermaid source.
- Any generated block with no reliable source mapping uses source fallback.

## Source Fallback Blocks

Source fallback is an embedded source editor for a single Markdown source range
inside rendered edit mode.

Required behavior:

- It appears in place of the rendered block, inside the same tab.
- It edits the same source buffer, not a copied string.
- Leaving the fallback editor returns to rendered display if parsing succeeds.
- Escape exits fallback edit focus without losing changes.
- Unsupported blocks must be obvious as source-editable regions, not broken
  rendered output.

Fallback is required for:

- fenced code blocks in the first milestone
- raw HTML blocks
- frontmatter
- malformed tables
- ambiguous nested formatting ranges
- any block where a direct rendered edit would be lossy

## Rendering and Mapping Requirements

The rendered editor needs a stable bidirectional mapping:

- source byte range to rendered node
- rendered caret position to source byte offset
- rendered selection to one or more source ranges
- source edit delta to rendered invalidation range

The current `markdown::RenderedText` mapping can be reused for text, links,
selection, and source-click behavior. The new editor needs to lift this mapping
from "click to jump" into "edit to patch source".

Mapping rules:

- Use UTF-8 byte offsets internally where existing Markdown and buffer APIs
  require them.
- Convert carefully at grapheme boundaries for caret movement.
- Do not allow a caret position inside hidden delimiter syntax unless the user
  enters source fallback.
- For formatted spans, rendered text maps to the inner content range by default.
- Selecting the whole rendered formatted span can include delimiters when a
  command needs to unwrap or delete the style.
- Generated text that has no source range is not directly editable.

## Architecture Plan

### New Crate or Module

Add a new module under `crates/markdown_preview` or a new crate named
`markdown_editor`. The first implementation should prefer a module under
`crates/markdown_preview` to reuse the existing parser, image resolver,
Markdown settings, and tests.

Proposed types:

- `RenderedMarkdownEditor`
- `RenderedMarkdownEditorMode`
- `RenderedMarkdownBlock`
- `RenderedMarkdownSelection`
- `RenderedMarkdownEdit`
- `MarkdownSourceMapper`
- `SourceFallbackEditor`

### Workspace Item Integration

The new rendered editor must implement the same workspace item contracts that
the normal editor relies on:

- tab title and path come from the underlying Markdown buffer
- `ItemBufferKind` exposes the real buffer
- save and close delegate to the real buffer
- serialization stores file path and rendered/source mode
- restoration opens the Markdown buffer and restores the selected mode

The existing preview item should remain serializable as-is. Do not repurpose
its database records for rendered edit mode.

### Editor Buffer Integration

All edits must go through the existing `Editor` or buffer edit APIs so that:

- undo/redo works
- dirty state works
- save works
- collaboration and remote buffers have a single source of truth
- file watchers and diagnostics continue to observe normal buffer changes

The rendered editor may keep an internal hidden `Editor` entity for the source
buffer, but it must not create an independent text copy.

### Rendering Integration

The first implementation should reuse:

- `markdown::Markdown`
- `markdown::MarkdownElement`
- `MarkdownStyle`
- existing image resolver behavior
- existing code block renderer where possible

Additional event hooks are required for:

- single-click caret placement
- rendered text input
- rendered selection painting
- composition input
- context menu commands
- structured block controls

### Input Method Editor Support

IME behavior is required because Japanese text editing is a primary use case.

Rendered edit mode must support:

- composition start, update, and commit
- underlined preedit text at the rendered caret
- cancellation without committing source edits
- correct insertion after conversion
- no duplicate text when committing composition

Implementation must test Japanese input in paragraph text, heading text, table
cells, and list items.

## UI Requirements

Rendered edit mode must feel like a document editor, not a preview panel.

Required UI details:

- active caret is visible in rendered text
- selected rendered ranges use normal selection colors
- block hover controls are subtle and do not shift layout
- link/image/table popovers are keyboard accessible
- source fallback blocks are visually distinct but still integrated into the
  document flow
- dirty indicator remains on the tab exactly as source mode
- command palette action names clearly distinguish preview vs rendered editor

No first-run instructional text should be required in the editor area.

## Search, Replace, and Navigation

First milestone:

- find searches rendered visible text
- selecting a find result moves the rendered selection and source selection
- replace can fall back to source mode if the replacement crosses hidden
  Markdown syntax

Required later:

- find options for rendered text vs source text
- replace across rendered selections where mapping is unambiguous
- outline navigation works from rendered headings

## Persistence and Restore

Workspace restore must preserve:

- open Markdown files
- source vs rendered edit mode
- optional source/rendered split mode
- scroll position per mode
- selection/caret position per mode

Do not persist parsed Markdown or rendered layout. Recompute from the buffer on
restore.

## Performance Requirements

- Typing latency in normal paragraph text should remain comparable to source
  editor typing for medium Markdown files.
- Reparse should be incremental if the existing Markdown parser supports it;
  otherwise reuse the current debounce behavior initially.
- Large files must not block the UI while reparsing.
- Images and diagrams should reuse existing cache behavior.
- Source fallback must be available for blocks that are too expensive to map or
  render interactively.

Initial acceptable threshold:

- files up to 5,000 Markdown lines remain usable
- typing in a paragraph updates within one frame for the local edit and within
  the existing preview debounce window for surrounding re-render

## Error Handling

- If parsing fails, keep the last known rendered document and show source
  fallback for the failing block or document.
- If a mapping cannot be resolved, do not guess. Open source fallback for that
  block.
- If a source edit conflicts with an external edit, reparse from the source
  buffer and preserve the nearest valid rendered caret.
- Never drop unsaved source changes when toggling modes.

## Milestones

### Milestone 1: Same-Tab Rendered Item Skeleton

- Add rendered edit mode action.
- Toggle current Markdown editor tab between source and rendered mode.
- Keep one tab identity and one source buffer.
- Render the document using the existing Markdown rendering pipeline.
- Preserve save, close, dirty state, undo, redo, tab title, and restore.
- Direct edit support can initially be limited to task checkbox toggles and
  source fallback blocks.

### Milestone 2: Text Blocks

- Direct caret and selection in headings and paragraphs.
- Typing, delete, backspace, enter, copy, cut, paste.
- Bold, italic, inline code, and link editing for simple inline ranges.
- IME support for Japanese text.

### Milestone 3: Lists and Links

- Structured list editing.
- Link popover editing.
- Image node selection and alt/path editing.
- Robust undo grouping for rendered edits.

### Milestone 4: Tables

- Cell editing.
- Row and column operations.
- Alignment preservation.
- Malformed-table fallback.

### Milestone 5: Advanced Blocks and Polish

- Code block inline editing or high-quality block fallback.
- Mermaid/source fallback workflow.
- Search and replace in rendered mode.
- Accessibility, keyboard navigation, and performance work.

## Acceptance Tests

The implementation is not complete unless these scenarios pass:

- Open `README.md`, toggle rendered edit mode, close tab with unsaved changes,
  and receive the same save prompt as source mode.
- Toggle source -> rendered -> source and verify byte-for-byte source is
  unchanged without edits.
- Type Japanese text in a paragraph through IME and verify exactly one committed
  string appears in source.
- Edit a heading title in rendered mode and verify only heading text changes.
- Bold a rendered selection and verify Markdown delimiters are correct.
- Toggle a task checkbox and undo it.
- Edit a link label without changing URL.
- Edit a link URL without changing label.
- Insert a new list item with Enter and verify marker type and indentation.
- Indent and outdent a nested list item.
- Edit a table cell and verify the source table remains valid.
- Insert and delete a table row.
- Double-click a Mermaid diagram and edit its source fallback.
- Open the same file in two splits, render one split, edit in the other, and
  verify rendered mode updates without losing caret.
- Restore workspace with rendered mode open and verify the same Markdown file
  returns in rendered mode.
- Save from rendered mode and verify the file on disk contains Markdown source.

## Implementation Notes From Current Code

Important existing files:

- `crates/markdown_preview/src/markdown_preview_view.rs`: action registration,
  active editor binding, source-to-preview debounce, rendered source click, link
  handling, image resolution, checkbox source edits, serialization tests.
- `crates/markdown/src/markdown.rs`: Markdown parsing, rendered text mapping,
  text selection helpers, link source ranges, image rendering, and tests for
  source/rendered mapping.
- `crates/zed_actions/src/lib.rs`: action namespace definitions.
- `crates/theme_settings/src/settings.rs`: Markdown preview font and theme
  settings that rendered edit mode should reuse or deliberately override.

The highest-risk implementation area is not rendering Markdown. It is editing
rendered text while preserving Markdown source syntax and Zed's editor item
contracts.

## Current Branch Status

Branch `docs/markdown-rendered-editor-spec` contains the Milestone 1 foundation
for same-tab rendered Markdown editing:

- `markdown::OpenRenderedEditor` replaces the active Markdown source `Editor`
  item with a `MarkdownPreviewView` in `RenderedEditor` mode in the same pane
  and at the same tab index.
- `markdown::OpenSourceEditor` restores the hidden source `Editor` for the same
  Markdown buffer.
- `markdown::ToggleRenderedEditor` switches between those two states.
- `ctrl-shift-m` on Windows/Linux and `cmd-shift-m` on macOS toggle rendered
  mode without replacing the existing preview shortcuts.
- Rendered mode delegates tab title, icon, tooltip, project path, dirty state,
  capability, save, save-as, reload, read-only toggle, conflict/deleted-file
  state, navigation, and deactivation behavior to the hidden source `Editor`.
- Rendered mode keeps the item buffer kind as `Singleton` so pane deduplication,
  dirty checks, close prompts, and save behavior continue to treat the tab as
  the Markdown file.
- Clicking rendered text in `RenderedEditor` mode moves the hidden source
  editor cursor to the corresponding Markdown source offset.
- Rendered mode registers a GPUI input handler while focused, so text input and
  IME composition are routed through the hidden source `Editor` and edit the
  Markdown buffer rather than a detached preview copy.
- Hidden source `Editor` selections are synchronized into the Markdown renderer
  selection state, which lets the rendered surface reuse the existing
  source-range selection highlight machinery.
- Empty renderer selections paint a caret at the mapped source position, and
  rendered-mode clicks keep focus on the rendered view while moving the hidden
  source editor cursor.
- Focused rendered mode relays core edit actions to the hidden source `Editor`:
  newline, newline-above, newline-below, backspace, delete, tab, backtab,
  indent, outdent, paste, undo, and redo.
- Task checkbox toggles continue to edit the source Markdown range directly.
- Focused tests verify same-tab replacement/restoration, dirty-state
  propagation from the source buffer, and input-handler edits into the source
  buffer, renderer selection synchronization, and basic edit-action relay.

This status is intentionally not equivalent to Office Viewer yet. The following
requirements remain incomplete and must be implemented before calling the
feature done:

- typing directly into rendered paragraphs, headings, list items, table cells,
  and link labels
- source-preserving rich edit commands such as bold, italic, heading level, link
  edit, list indent/outdent, and table row/column operations
- copy/cut/paste semantics that distinguish rendered plain text from Markdown
  source
- rendered IME candidate bounds and composition underline placement
- rendered-mode find/replace over editable source mappings
- source fallback editors for code blocks, Mermaid, math, raw HTML, and other
  lossy blocks
- split source/rendered mode inside one tab content area

## Open Design Questions

- Should rendered mode replace the active `Editor` item in the pane, or should
  `Editor` become able to render a Markdown buffer through a different display
  layer?
- Should source fallback use a full `Editor` entity per block or a lighter
  text-input component bound to a source range?
- Should copy default to rendered text or Markdown source? This spec chooses
  rendered text by default to match document-editor expectations.
- Should `default_open_mode = rendered` be global or workspace-scoped?
- How should collaborative cursors be represented in rendered mode when other
  participants are editing hidden Markdown syntax?

Resolve these before implementing Milestone 2.
